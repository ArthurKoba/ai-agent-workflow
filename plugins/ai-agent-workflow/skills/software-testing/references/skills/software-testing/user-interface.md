# Тестирование пользовательского интерфейса

## Пользовательский переход

Задай исходное состояние, действие пользователя и наблюдаемый итог. Находи элементы по роли, доступному имени или устойчивому признаку. Проверяй внутреннее устройство компонента, если оно входит в его публичный контракт.

- Для формы проверь принятие, отклонение и исправление ввода. Различай начатую отправку и её видимый итог. После отказа проверь, какие данные сохранились, доступен ли повтор и куда попал фокус.
- Для доступности проверь имена, роли, клавиатурное управление и получение важного сообщения вспомогательной технологией, если оно должно объявляться. Автоматическая проверка атрибутов даёт часть свидетельства.
- Для сравнения внешнего вида зафиксируй размер, тему, шрифты, язык и данные. В поддерживаемых размерах проверь, доступно ли действие, в том числе при прокрутке. Ограничь область сравнения и обновляй эталон по понятному изменению требований. Для оценки удобства используй [Interface Design Review](../interface-design-review.md).

## Веб-интерфейс

- Для состояний компонента управляй данными и очередностью ответов. При смене фильтра сначала доставь актуальный ответ, затем старый. Проверь актуальный экран после обработки обоих, включая позднюю ошибку, если она меняет состояние.
- Используй браузер для нативной валидации формы, фокуса, раскладки и навигации. Отправь форму штатным действием. Если доступны кнопка и клавиатура, проверь оба пути. Проверь прямой вход, возврат или перезагрузку, когда они меняют пользовательский итог. При серверном рендеринге проверь первое действие при задержанной гидратации, если интерфейс уже выглядит доступным.
- Сквозной сценарий нужен, когда результат зависит от совместной работы клиента и сервера. Например, сохрани объект через интерфейс, перезагрузи страницу и проверь, что он доступен. Варианты формата и совместимость версий проверяй на [границе обмена](client-server.md).
- Для TypeScript запускай проверку типов по конфигурации проекта отдельно от проверки поведения на входных данных. Для изменившегося публичного типового API сверяй допустимые и недопустимые вызовы. Тест интерфейса должен показать, что получит пользователь, если фактический ответ имеет неверную форму.

## Desktop и нативное поведение

Для Qt на C++ или Python проверка модели и события, направленного виджету, подходит для локального состояния. Дожидайся применения результата в интерфейсе. Для системного диалога, передачи фокуса, устройства или графической гарантии используй целевую ОС и нужную оконную среду. Например, отмени диалог и проверь, куда приходит следующий ввод. При восстановлении окна закрой приложение и запусти новый процесс с тем же изолированным тестовым профилем. Связывай результат рендера с использованным графическим режимом. Offscreen проверяет выбранный путь отрисовки. Установку и запуск пакета проверяй по [главе про развёртывание](operations.md#развёртывание-и-внешние-системы).

## Нативные мобильные приложения

Различай пересоздание экрана и потерю процесса. Например, на Android черновик может пережить поворот в памяти. Для восстановления после системного завершения проверь возврат в сохранённую задачу в новом процессе. Если он должен пережить новый запуск без сохранённой задачи, проверь это отдельно. Для разрешений начни с известного состояния и проверь первоначальный отказ и отзыв доступа. При записи без сети проверь локальный результат и статус ожидания после перезапуска, затем итог синхронизации и число эффектов после восстановления связи.

Используй симулятор или эмулятор, когда он воспроизводит нужное свойство. Для аппаратных или фоновых гарантий, зависимых от устройства, используй релизную сборку на физическом устройстве. Если отладчик меняет жизненный цикл, как при приостановке iOS, запускай без него.
