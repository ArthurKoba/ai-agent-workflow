# Подготовка проекта и сред разработки

Загружать при **создании репозитория**, первом развёртывании среды
разработчика/CI или целенаправленном изменении toolchain, форматирования,
типизации и Git hooks. Это не инструкция по архитектуре приложения.

## Граница применения

- Сначала изучить `AGENTS.md`/README, манифесты, lockfile, CI, существующие
  hooks и фактически используемые локальную, тестовую и production-среды.
- Для **нового** TypeScript-проекта стандарт — **Bun**, для **нового**
  Python-проекта — **uv**. Это обязательные исходные решения для bootstrap,
  а не разрешение молча переписать уже работающий чужой проект.
- При существующем ином согласованном toolchain сохранить его до явного
  решения о миграции; зафиксировать исключение в локальной документации.
- Конкретные версии, команды, секреты, адреса и особенности среды принадлежат
  репозиторию проекта. Универсальный навык задаёт требования и проверки,
  не подменяя локальные инструкции.

## Минимальный контракт любой среды

1. Закрепить версии runtime и пакетного менеджера, коммитить lockfile.
   Зависимости в CI устанавливать воспроизводимо, без незаметного обновления.
2. Настроить отдельно команды **format-check**, **lint**, **type-check**,
   **tests** и при наличии артефакта — **build**. Единый `verify`/аналог
   должен завершаться ненулевым кодом при провале обязательного этапа.
3. Правила запускать не только в IDE: те же проверяемые команды должны
   исполняться через tracked Git hooks и независимо в CI.
4. Предусмотреть `.env.example` без секретов, отсутствие credentials и
   локальных `.env` в Git, явную конфигурацию DEV/TEST/production.
   Не копировать production secrets в разработку/тесты.
5. Перед первым коммитом проверить авторскую идентичность Git
   (`git var GIT_AUTHOR_IDENT`); настроить её для подтверждённого
   пользователя/агента **локально в репозитории** или через утверждённый
   credential provider. Не угадывать имя/email и не менять глобальную
   конфигурацию другой среды.
6. README должен объяснять установку, запуск, тесты, сборку и
   восстановление hooks на новом checkout.
7. Не подменять качество отключением ошибок, глобальными исключениями и
   флагами обхода. Любое несовместимое правило отключать адресно,
   с пояснением конкретной причины.

## Новый TypeScript-проект

- Использовать **Bun** для зависимостей и сценариев: `bun.lock`,
  `bun install --frozen-lockfile`, `bun run <script>`.
  Версию Bun закрепить в принятом репозиторием toolchain/CI.
- Включить строгую проверку TypeScript (`strict`); дополнительно включать
  применимые `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`
  и запрет неиспользуемых переменных/параметров, не ломая внешний контракт.
- Использовать **Biome** как основной formatter/linter с максимально
  строгими **применимыми** правилами, включая `linter.rules.all`, и
  блокирующими lint/format проверками. Исключения на уровне конкретных правил
  и областей допустимы только с обоснованием (например, правила для
  чужого UI-фреймворка или сгенерированного кода). Не объявлять
  предупреждения успешными.
- Проверять не только синтаксис: type-check и тесты входят в общий gate,
  а build — когда проект собирает доставляемый артефакт.
- Особенности Vue/TS и архитектурное размещение принадлежат
  `frontend-engineering/vue-typescript.md` и фактическим правилам проекта.

## Новый Python-проект

- Использовать **uv** для окружения и зависимостей: `pyproject.toml`,
  `uv.lock`, `uv sync --frozen`, `uv run <tool>`.
  Версию Python/uv закрепить для локальной разработки и CI.
- Настроить **Ruff** (lint + formatter) со строгим набором применимых
  проверок, рассматривая `select = ["ALL"]` как стартовую точку.
  Несовместимые/конфликтующие правила исключать точечно и документировать.
- Включить **mypy** в строгом режиме (`strict = true`) и определить
  область проверяемого исходного кода. Не замалчивать ошибки широкими
  `ignore_errors` или неограниченными `Any`.
- В общий gate включить `uv run ruff check`,
  `uv run ruff format --check`, `uv run mypy`, тесты
  (например, `uv run pytest`) и релевантную сборку.
- Предметные правила Python не дублировать здесь:
  см. `software-engineering/python.md`.

## Git hooks и CI — обязательный этап bootstrap

- Предпочитать **отслеживаемые в Git** скрипты hooks. Установить их для
  текущего checkout через утверждённый менеджер hooks или локальный
  `core.hooksPath`. Самого файла в репозитории недостаточно: Git
  должен использовать правильный путь, а hook должен быть исполняемым.
- **pre-commit:** быстрые проверяемые операции для изменённых файлов,
  если это принято проектом; не подменяет общую проверку.
- **pre-push (обязателен):** запускает полный релевантный
  `verify`/quality gate. Любая ошибка останавливает push. Не допускать
  заглушки, всегда возвращающей success.
- При новом clone/checkout установить hooks, проверить фактический
  `core.hooksPath`, наличие исполняемого `pre-push`, соответствие его
  команды объявленному gate и **пробный запуск проверки**.
  Повторять эту проверку при переинициализации среды и перед первым push.
- CI на сервере должен отдельно запускать тот же gate для PR/MR:
  локальные hooks **не гарантируют** защиту от bypass или API-записей.
  Не отключать hooks через `--no-verify`/`HUSKY=0` или подмену
  `core.hooksPath`; исправлять падающие проверки.
- Перед конкретным commit/push применять `skills/git-workflow.md`.
  Если hook отсутствует/неактивен и его нельзя установить в разрешённой
  среде, явно фиксировать блокер и не утверждать, что push защищён.

## Приёмка bootstrap

Подтвердить на **реальном новом checkout**, что команды установки,
`verify`, исполняемый pre-push и CI работают. Один раз специально
проверить fail-closed: намеренно неуспешная проверка должна останавливать
hook; после этого восстановить чистое состояние. Не считать наличие
файлов достаточным доказательством установки или работы.
