
# Frontend-стандарты

Эту заметку нужно читать при работе с frontend-кодом.

Модуль ориентирован на Vue 3 + TypeScript и применимые Vite/Pinia/Vue Router проекты. Package manager и scripts определяются репозиторием.

## Общая дисциплина

- Выполнять ровно запрошенную frontend-задачу.
- Следовать существующей структуре frontend-приложения и стилю соседних файлов.
- Не добавлять новые UI-библиотеки, state-management, CSS-framework или build plugins без подтверждённой необходимости и проверки project dependency policy.
- Перед созданием нового компонента, store, view или helper проверить, нет ли подходящего существующего файла.
- Не переписывать стартовый шаблон, архитектуру или дизайн шире необходимого для задачи.

## Структура frontend

- Следовать фактической архитектуре репозитория (`src/`, FSD или другой объявленной схеме), а не навязывать универсальное дерево папок.
- Entry point, router, state, assets и public files держать у существующих владельцев проекта.
- При архитектурном переносе использовать `feature-sliced-design.md` только если FSD выбран проектом или является целью задачи.

## Vue и TypeScript

- Использовать Vue 3 Composition API и `<script setup lang="ts">` для новых компонентов.
- Типизировать props, emits, composables, stores и функции.
- Не использовать `any` без явного основания; если тип неизвестен, сузить его через union, interface, type alias или runtime-check.
- Для импортов из `src` использовать alias `@/`, если это улучшает читаемость и поддерживается конфигом.
- Сохранять импорты в начале файла и удалять неиспользуемые импорты.
- Не хранить бизнес-правила API или сложные преобразования данных прямо в template.
- Не мутировать props напрямую.
- Для derived state использовать `computed`, для побочных эффектов — `watch`/`watchEffect` только при необходимости.

## Компоненты

- Компонент должен иметь понятную ответственность.
- Локальную UI-логику держать внутри компонента, переиспользуемую логику выносить в composable только при реальном повторном использовании или сложности.
- Не создавать слишком мелкие компоненты, если они ухудшают читаемость сценария.
- Не смешивать routing, глобальное состояние и низкоуровневую разметку в одном компоненте без необходимости.
- Состояния загрузки, ошибки и пустых данных должны быть явными, если компонент работает с асинхронными данными.

## Router

- Маршруты объявлять в `src/router/index.ts` или в существующей роутерной структуре.
- Views, которые не нужны на первом экране, можно подключать lazy import через `() => import(...)`.
- Route names должны быть стабильными и описательными.
- Не размещать бизнес-логику и API-вызовы прямо в route config.

## Pinia

- Store использовать для состояния, которое нужно нескольким компонентам или переживает смену route.
- Локальное состояние компонента не переносить в Pinia без необходимости.
- Actions должны быть типизированы и содержать явные состояния ошибок/загрузки, если работают с асинхронными операциями.
- Не хранить в store производные значения, которые можно выразить getter/computed.

## CSS и UI

- Сохранять существующий CSS-подход, если пользователь не просит изменить дизайн-систему.
- Проверять адаптивность для мобильного и desktop viewport, если задача меняет layout.
- Не допускать наложения текста, кнопок и интерактивных элементов.
- Текст в кнопках и компактных элементах должен помещаться без горизонтального переполнения.
- Не добавлять декоративные эффекты, анимации или изображения, если они не нужны для задачи.
- Для интерактивных элементов учитывать hover, focus, disabled и loading states, когда они применимы.

## Сборка и проверки
- Для frontend-проверки по умолчанию использовать команды из `package.json`.
- Предпочитать минимально достаточную нетестовую проверку под риск изменения, а не автоматически запускать полную сборку.
- После изменений в Vue/TypeScript запускать repository-provided type-check, когда правка затрагивает script, props, stores, composables, router typings, imports или public API и project acceptance требует эту проверку.
- После изменений, которые могут нарушить форматирование, порядок импортов или lint rules, запускать repository-provided lint/format check или более узкую проверку.
- Полную frontend build не запускать автоматически после каждого микропатча.
- Запускать repository build, когда есть конкретный риск сборочной ошибки: изменены Vite config, entry point, `index.html`, build scripts, dependency setup, asset imports, lazy imports, route-level code splitting, plugin/provider bootstrap, alias/path config или package exports.
- Запускать repository build, если этого требует пользователь/project acceptance или ошибку сборки/runtime нельзя доказать более узкой проверкой.
- Для обычных локальных изменений компонента, стилей, текста, FSD-переноса без сложных dynamic imports или небольшого обновления public API обычно достаточно project type-check и/или lint, если они применимы.
- Для визуальных изменений запускать dev server, build или preview только если нужно реально проверить результат в браузере; если пользователь готов проверить сам, достаточно сообщить, что визуальная проверка не запускалась.
- Не запускать долгие или нерелевантные проверки без необходимости. Если build пропущен осознанно, кратко указать это в финальном ответе.

## Чеклист перед завершением frontend-задачи
- Изменения ограничены запрошенной frontend-задачей.
- Новые файлы размещены в существующей структуре `src/`.
- Vue-компоненты используют `<script setup lang="ts">`, если нет причины сохранить старый стиль.
- Props, emits, stores и функции типизированы.
- Нет лишнего `any`, неиспользуемых импортов и мёртвого кода.
- Layout проверен на отсутствие очевидных переполнений и наложений, если задача меняла UI.
- Запущены минимально достаточные repository-provided проверки под риск изменения.
- Full build запущен только при конкретном сборочном риске или когда этого требует project acceptance; если build осознанно пропущен, validation level не завышен.
- После массового рефакторинга выполнить поиск по удаляемым именам, CSS tokens, старым компонентам, alias-путям и семантическим тегам, которые должны были исчезнуть или сменить владельца.
- Если правка исправляет ранее допущенную ошибку, явно проверить весь класс похожих случаев, а не только найденный пример.
