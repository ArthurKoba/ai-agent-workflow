
# UI и вёрстка

Эту заметку нужно читать при задачах, которые меняют интерфейс, вёрстку, визуальную структуру, состояния компонентов, формы, панели, списки, таблицы, навигацию или добавляют новые UI-элементы.

## Основной принцип

UI нужно собирать из существующей дизайн-системы и компонентов проекта. Новый элемент добавляется не как изолированный фрагмент разметки, а как часть существующего интерфейсного паттерна: с корректным состоянием, адаптивностью, доступностью и предсказуемым поведением.

## Перед добавлением UI-элемента

- Проверить соседние views/components и повторить существующие паттерны разметки, отступов, размеров, состояний и именования.
- Проверить, есть ли уже подходящий компонент в `src/components`, `src/components/ui`, `src/shared` или другом принятом UI-слое проекта.
- Если проект использует shadcn/shadcn-vue, сначала искать подходящий готовый компонент или block, а не писать примитив с нуля.
- Если доступен shadcn MCP, использовать его для поиска, просмотра документации и установки компонентов из registry.
- Если shadcn MCP недоступен, использовать CLI `shadcn-vue` и официальную документацию shadcn-vue.
- Не добавлять новую UI-библиотеку, CSS-фреймворк, icon set или headless stack без подтверждённой необходимости и проверки существующего project design system/dependency policy.

## Использование shadcn-vue

- Для Vue-проекта использовать `shadcn-vue`, а не React-версию `shadcn/ui`.
- Компоненты shadcn размещать в каталоге, указанном в `components.json`, обычно `src/components/ui`.
- Добавлять shadcn-компоненты через CLI или MCP, чтобы вместе с компонентом были добавлены зависимости и связанные файлы.
- Не редактировать сгенерированный shadcn-компонент шире необходимого; продуктовую композицию собирать в отдельном компоненте или view.
- Для классов использовать `cn()` из `@/lib/utils`, если нужно объединять условные Tailwind-классы.
- Для иконок использовать подключённую библиотеку из `components.json`, обычно `lucide` / `@lucide/vue`.


### Базовые shadcn-стили и компоненты

- Если пользователь просит сбросить, обновить или привести стили к базе shadcn, сначала использовать shadcn MCP/CLI или сгенерированный baseline, а не собирать CSS вручную.
- Перед ручной заменой CSS проверить, не покрывается ли задача параметрами, variants, slots или готовым компонентом shadcn-vue.
- При массовом переходе на shadcn сначала загрузить актуальный список компонентов/blocks через shadcn MCP или CLI, затем принимать решения по замене.
- Не оставлять кастомные design tokens, reset-файлы, глобальные селекторы и hover-правила, если они дублируют или переопределяют базовые shadcn tokens без явной причины.
- Если удаляется кастомный token, сначала найти все его использования и заменить на семантический shadcn token: `primary`, `foreground`, `muted`, `border`, `ring`, `destructive` и т.п.

## Правила композиции интерфейса

- Выбирать семантический компонент под задачу: `Button` для действий, `Input`/`Textarea` для ввода, `Select`/`Combobox` для выбора, `Dialog` для модальных сценариев, `DropdownMenu` для меню действий, `Tabs` для переключения представлений, `Table` для табличных данных.
- Не заменять стандартный контрол произвольным `div`, если есть нативный или shadcn-компонент с нужной семантикой.
- Формы собирать с явными label, description/error state и доступной связью label-control.
- Для повторяющихся элементов использовать стабильные размеры, `min/max`, grid/flex constraints и предсказуемые gap/padding.
- Не вкладывать карточки в карточки без сильной структурной причины.
- Не делать декоративные wrapper-слои, если они не несут ответственности за layout, состояние или семантику.

## Адаптивность и устойчивость layout

- Проверять поведение на мобильном и desktop viewport, если меняется layout.
- Текст в кнопках, badges, tabs, table cells и compact controls должен помещаться без горизонтального overflow.
- Длинные значения должны переноситься, обрезаться с понятным `truncate`, либо отображаться в layout, который выдерживает длинный контент.
- Hover, focus, active, disabled, loading и empty states должны быть предусмотрены там, где пользователь с ними столкнётся.
- Интерактивные элементы должны иметь достаточную область клика и не перекрываться соседними элементами.
- Не использовать viewport-зависимое масштабирование шрифта для обычного UI.


### Диагностика layout-проблем

- Для проблем с отступами и скачками layout сначала определить, какой условный элемент меняет геометрию: breadcrumb, header action, sidebar, scroll container, slot content или route wrapper.
- Не лечить общий padding/margin до проверки DOM-ответственности: layout отвечает за каркас и scroll areas, page/widget отвечает за содержимое, header/sidebar отвечают только за собственную сетку.
- Если один и тот же смысловой контейнер (`main`, `section`, header shell, scroll area) появляется в layout и page одновременно, сначала выбрать единственного владельца семантики и убрать дублирование.
- При изменении header/layout проверить страницы с breadcrumb и без breadcrumb, чтобы условный элемент не менял внешний отступ или ширину actions.


### Stable Layout Standards

Stable layout означает, что UI сохраняет предсказуемую геометрию при смене данных, состояний и viewport. Для таблиц, списков, toolbar, pagination, tabs, filters и compact controls заранее задавать стабильные constraints: `min/max`, фиксированные зоны actions, предсказуемые grid/flex tracks, scroll container или явно выбранный mobile layout.

Перед изменением плотных UI-блоков проверить состояния, которые чаще всего ломают геометрию: длинный текст, пустые данные, loading, error, disabled controls, скрытые колонки, активные filters, выбранные строки, узкий viewport и отсутствие optional slot content.

Для таблиц использовать один из устойчивых responsive-паттернов: horizontal scroll для сохранения табличной формы, сокращённый набор колонок или mobile card/list mode. Нельзя оставлять мобильный viewport на случайное сжатие всех колонок, если это делает текст и controls нечитаемыми.

Toolbar, filters, table body и pagination должны иметь постоянные зоны. Появление bulk actions, errors, empty state или column settings не должно менять внешний каркас блока так, чтобы пользователь терял контекст.

Если задача касается reusable table shell или table slots, дополнительно подключать `standalone-table.md`.

## Цвета, темы и Tailwind

- Использовать design tokens и CSS variables проекта: `background`, `foreground`, `primary`, `muted`, `border`, `ring`, `destructive` и другие токены shadcn.
- Не хардкодить произвольные цвета, если есть семантический токен.
- Поддерживать dark mode, если проект уже использует shadcn CSS variables или `.dark`.
- Tailwind-классы держать читаемыми; повторяющиеся сложные комбинации выносить в компонент, variant или helper только при реальном повторении.
- Не добавлять декоративные эффекты, анимации, gradients или изображения без продуктовой необходимости.

## Проверка перед завершением

- UI-элемент добавлен через существующий паттерн или через shadcn-vue, если это подходит.
- Нет лишней новой библиотеки или самодельного контрола там, где есть готовый компонент.
- Layout не ломается на мобильном и desktop viewport.
- Текст, иконки и controls не перекрываются и не вылезают из контейнеров.
- Состояния loading/error/empty/disabled учтены, если применимы.
- Запущены релевантные проверки проекта: type-check/build/lint или более узкая команда.
