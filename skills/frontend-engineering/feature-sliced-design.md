
# FSD-архитектура frontend

Эту заметку нужно читать при создании, изменении или ревью frontend-архитектуры по Feature-Sliced Design: слои, slices, segments, публичные API, размещение состояния, API, таблиц, переводов и правила импортов.

## Когда читать эту заметку

Подключать это правило, если задача касается:

- структуры frontend-каталогов или перехода к FSD;
- создания, переноса или ревью кода в `app`, `pages`, `widgets`, `features`, `entities`, `shared`;
- выбора слоя для компонента, composable, store, API-функции, типа, таблицы, фильтра, перевода или форматтера;
- толстых `pages` или `widgets`, дублирования таблиц, смешивания UI, API и бизнес-логики;
- правил импортов, public API, slices и segments.

Если задача только меняет визуальную вёрстку без архитектурного переноса, дополнительно читать UI-правила, но FSD применять только к затронутым архитектурным границам.

## Связанная заметка с примерами
Подробные разборы спорных размещений вынесены в `feature-sliced-design-examples.md`. Читать её дополнительно, когда:

- есть сомнение между `widgets`, `features`, `entities` и `shared`;
- виджет начинает содержать типы сущности, API, таблицы, фильтры, действия или переводы;
- нужно разложить таблицу, список, toolbar, фильтры, bulk actions, i18n или entity UI по слоям;
- нужно ревьюить или исправлять FSD-нарушения, особенно анти-паттерн “всё в widget”.

## Главная модель принятия решений

FSD — это не схема папок, а правило размещения ответственности. Перед добавлением или переносом кода нужно определить не техническую форму файла, а причину его изменения.

Главный критерий: код размещается там, где находится причина его будущих изменений.

- Если код меняется из-за запуска приложения целиком, он относится к `app`.
- Если код меняется из-за маршрута, URL, route params или конкретного экрана, он относится к `pages`.
- Если код меняется из-за композиции самостоятельного блока страницы, он относится к `widgets`.
- Если код меняется из-за действия пользователя или бизнес-сценария, он относится к `features`.
- Если код меняется из-за правил предметной области, полей, статусов или базового отображения сущности, он относится к `entities`.
- Если код не знает бизнес-домен и меняется из-за технической инфраструктуры или дизайн-системы, он относится к `shared`.

Нельзя выбирать слой по типу файла. Vue-компонент может быть `shared`, `entity`, `feature`, `widget` или `page` в зависимости от смысла. API-функция может быть `shared`, `entity` или `feature` в зависимости от ответственности. Store может быть `app`, `entity`, `feature`, `widget` или `page`, если его состояние принадлежит соответствующему уровню.

## Слои и направление зависимостей

Использовать стандартные FSD layers сверху вниз: `app`, `pages`, `widgets`, `features`, `entities`, `shared`.

Разрешённое направление зависимостей: `app -> pages -> widgets -> features -> entities -> shared`.

Модуль может импортировать только нижележащие слои. Нижний слой не должен знать о верхнем. Это означает, что `entities` не знают о `features`, `features` не знают о `widgets`, `widgets` не знают о `pages`, а `shared` не знает ни о каком бизнес-домене.

`app` и `shared` являются особыми слоями. `app` собирает приложение и может подключать нижние слои как composition root. `shared` находится внизу и может иметь внутренние зависимости между собственными модулями, но не должен зависеть от домена.

Слой `processes` не добавлять без отдельного явного основания: в современной практике он редко нужен и часто становится лишним местом для размытой сценарной логики.

## Дерево выбора слоя

Перед созданием файла пройти короткую проверку:

1. Код нужен для bootstrap, провайдеров, router, глобальных стилей или app-level setup? Это `app`.
2. Код является route entry, работает с route params или описывает конкретный экран? Это `pages`.
3. Код только собирает несколько готовых частей в самостоятельный блок страницы? Это `widgets`.
4. Код реализует действие пользователя: создать, удалить, отправить, подтвердить, экспортировать, изменить, применить? Это `features`.
5. Код описывает бизнес-сущность, её поля, статусы, типы, базовые API, форматирование или нейтральное отображение? Это `entities`.
6. Код универсален, не знает доменных слов и бизнес-правил? Это `shared`.
7. Если код используется только в одном месте и не имеет ясной самостоятельной ответственности, не создавать новый слой или slice заранее. Сначала оставить ближе к месту использования, пока не появится причина выделения.

## Ответственность `shared`

`shared` — фундамент приложения без знания предметной области. Он отвечает за инфраструктуру, универсальные UI-примитивы, технические helpers, базовые адаптеры и общие механики, которые можно перенести в другой проект без потери смысла.

В `shared` допустимы:

- дизайн-системные компоненты и UI-kit: кнопки, поля ввода, диалоги, карточки, базовая таблица, пагинация, skeleton, tooltip;
- инфраструктура API: HTTP-клиент, transport, interceptors, базовая обработка ошибок, request helpers;
- общие config/env/helpers без домена;
- технические composables: media query, debounce, local storage, clipboard, форматирование дат и чисел без бизнес-смысла;
- общая i18n-инфраструктура и универсальные фразы вроде загрузки, отмены, сохранения, пустого состояния.

В `shared` запрещены:

- типы доменных сущностей: пользователь, заказ, реферал, платеж, подписка;
- бизнес-правила, роли, статусы сущностей и условия доступа;
- entity-specific переводы, подписи колонок, доменные форматтеры;
- feature-specific компоненты: кнопки создания, удаления, экспорта, подтверждения действия;
- универсальные файлы-свалки, где смешаны helpers разных смыслов.

Текстовый пример: базовая таблица с пагинацией и slots относится к `shared`, потому что она не знает, какие данные отображает. Но колонка “статус пользователя” не относится к `shared`, потому что она знает доменную сущность и её статус.

## Ответственность `entities`

`entities` — слой предметной области. Entity — это не любой компонент и не любая таблица. Entity — это устойчивое бизнес-понятие приложения: пользователь, заказ, тариф, платёж, реферал, уведомление, проект.

В `entities` допустимы:

- доменные типы, DTO, схемы, мапперы и нормализация данных сущности;
- API-запросы, которые получают или изменяют данные сущности без привязки к конкретному пользовательскому сценарию;
- базовое состояние сущности, если оно описывает данные предметной области, а не одно действие;
- нейтральные UI-представления сущности: avatar, badge статуса, краткая карточка, строка списка, базовая таблица сущности;
- колонки, labels, статусы, форматирование и фильтры, если они описывают саму сущность и могут переиспользоваться в разных сценариях;
- entity-specific переводы: поля, статусы, базовые названия сущности.

В `entities` запрещены:

- действия пользователя и сценарии: создать, удалить, заблокировать, изменить роль, экспортировать, отправить приглашение;
- admin-only логика, права доступа конкретной страницы, toolbar и bulk actions;
- page layout, route-specific navigation и зависимость от URL-контекста;
- прямые импорты из `features`, `widgets`, `pages`, `app`;
- сборка крупных блоков, где участвуют несколько независимых сценариев.

Текстовый пример: бейдж статуса пользователя относится к `entities/user`, потому что статус является свойством пользователя. Кнопка блокировки пользователя относится к `features`, потому что это действие пользователя и бизнес-сценарий. Панель администрирования пользователей относится к `widgets` или `pages`, потому что она собирает таблицу, toolbar и действия в контексте экрана.

## Ответственность `features`

`features` — слой действий пользователя и бизнес-сценариев. Feature должна отвечать на вопрос “что пользователь делает?” или “какой сценарий выполняется?”. Если название звучит как действие, команда или use case, почти всегда это feature.

В `features` допустимы:

- формы, кнопки, диалоги и сценарии создания, редактирования, удаления, подтверждения, экспорта, импорта, отправки, применения;
- model/state конкретного действия: форма, validation, pending/error/success, selected items для сценария, optimistic update действия;
- API-команды, которые существуют ради конкретного действия, а не ради нейтрального получения сущности;
- сценарные permissions, если они относятся к возможности выполнить действие;
- тексты действия: заголовок диалога, submit, success/error сообщения, confirmation copy.

В `features` запрещены:

- вся таблица или вся секция страницы только потому, что внутри есть действие;
- базовое отображение сущности, которое нужно в разных сценариях;
- универсальные UI-компоненты и технические helpers;
- прямая зависимость от соседних features того же слоя;
- layout страницы, заголовки секций, сетки и композиция нескольких независимых действий как единый большой компонент.

Текстовый пример: “изменить роль пользователя” — feature, потому что пользователь выполняет действие, у него есть форма или control, API-команда, состояние выполнения и ошибки. “роль пользователя как поле в таблице” — entity, потому что это часть модели пользователя. “админская таблица пользователей с кнопками смены роли и удаления” — widget, потому что она собирает entity table и несколько features.

Feature не должна становиться мини-страницей. Если компонент содержит заголовок блока, сетку, несколько независимых действий, таблицу, фильтры и композицию разных сценариев, это уже `widgets` или `pages`, а сами действия нужно выделить в отдельные features.

## Ответственность `widgets`

`widgets` — крупные самостоятельные блоки страницы. Widget собирает `features`, `entities` и `shared` в осмысленную область интерфейса, но не владеет доменной моделью и не реализует действия с нуля.

В `widgets` допустимы:

- композиция таблицы сущности, toolbar, фильтров, действий, empty/loading/error states блока;
- локальная orchestration-логика: какие части показать, какие слоты передать, какие actions подключить, как разложить блок визуально;
- состояние композиции, если оно не является доменной моделью и не принадлежит одному действию;
- заголовки и тексты составного блока, если они относятся именно к этому блоку;
- контекстное связывание нескольких нижних слоёв для конкретной области страницы.

В `widgets` запрещены:

- доменные типы, DTO, мапперы и базовые API сущности;
- базовая таблица, универсальная пагинация, generic filters layout;
- реализация действий пользователя вместо подключения готовых features;
- хранение базовых entity UI: status badge, avatar, formatter, reusable columns;
- превращение одного widget в контейнер для всей страницы, нескольких доменов и всех сценариев.

Текстовый пример: `Admin Users` как блок может быть widget, если он собирает таблицу пользователей, actions создания/удаления/смены роли, toolbar и states. Но тип пользователя, его поля, статус, базовые колонки и API получения пользователей должны находиться в `entities/user`, а действия администратора — в `features`.

Главная защита от “жирных widgets”: если внутри widget появляется код, который можно назвать сущностью, действием или универсальным UI-инструментом, этот код нужно опустить в `entities`, `features` или `shared`. В widget остаётся только композиция.

## Ответственность `pages`

`pages` — route-level слой. Page представляет экран, связанный с маршрутом, и должна оставаться тонкой настолько, насколько позволяет текущая задача.

В `pages` допустимы:

- route entry и минимальная сборка экрана из widgets, features, entities и shared;
- работа с route params, query params, guards или page-level loading/error boundaries;
- layout конкретного экрана, если он не является переиспользуемым блоком;
- уникальная композиция, которая используется только на одной странице и пока не заслуживает отдельного widget.

В `pages` запрещены:

- reusable бизнес-компоненты, которые нужны другим страницам;
- универсальные таблицы, entity model, базовые колонки и форматтеры сущностей;
- реализация действий пользователя с нуля;
- копирование одного и того же блока между несколькими pages вместо выделения widget.

Текстовый пример: если экран состоит из одного уникального блока и нет признаков переиспользования, можно временно оставить композицию в page. Если блок получил собственную структуру, toolbar, states, несколько actions или начал повторяться, его нужно вынести в `widgets`, а page оставить route wrapper.

## Ответственность `app`

`app` — composition root всего приложения. Этот слой отвечает за запуск, глобальную инфраструктуру и подключение провайдеров.

В `app` допустимы:

- entrypoint приложения;
- router setup и route registration;
- providers, plugin setup, глобальные stores/plugins;
- инициализация i18n, темы, глобальных стилей;
- app-level config и shell приложения.

В `app` запрещены entity UI, feature UI, таблицы конкретных сущностей, бизнес-виджеты и сценарии конкретных страниц. Если код можно назвать пользовательским действием, доменной сущностью или блоком страницы, он не должен жить в `app`.

## Slices

Slices создаются внутри `pages`, `widgets`, `features`, `entities`. `app` и `shared` обычно делятся на технические модули/segments, а не на бизнес-slices.

Slice должен называться по бизнес- или продуктовому смыслу:

- для `entities` — существительное предметной области;
- для `features` — действие или use case;
- для `widgets` — самостоятельный блок интерфейса;
- для `pages` — экран или route.

Не создавать slice ради одного технического файла без самостоятельной ответственности. Не объединять несколько независимых сценариев в один slice только потому, что они находятся рядом на странице.

Прямые cross-imports между slices одного слоя запрещены по умолчанию. Если двум slices нужна общая логика, сначала проверить нижний слой: `features` могут разделить entity-контракт через `entities`, widgets могут разделить действие через `features`, а универсальный UI должен уйти в `shared`.

## Segments

Segments — техническое разделение внутри slice. Использовать только те segments, которые реально нужны текущему slice.

Стандартные segments:

- `ui` — компоненты, визуальное представление, presentation helpers;
- `model` — типы, stores, state, validation, selectors, composables состояния, бизнес-правила slice;
- `api` — endpoint functions, DTO, адаптеры внешнего API, относящиеся к slice;
- `lib` — локальные helpers slice, которые не являются общими для проекта;
- `config` — локальные настройки, i18n keys, feature flags, static config slice.

Не использовать как основные segments `components`, `hooks`, `composables`, `types`, `utils`, `helpers`. Такие названия группируют код по технической форме и размывают ответственность. Допустимы конкретные файлы с такими словами, если имя всё равно описывает назначение, например типы таблицы сущности или helper форматирования конкретного поля.

Не создавать обязательный набор segments заранее. Если slice содержит только UI и public API, этого достаточно.

## Public API
Каждый slice, который используется извне, должен иметь публичные точки входа.

Основной runtime public API предоставляется через `index.ts` или установленный в проекте эквивалент. Внешний код импортирует runtime-значения slice только через этот API, а не через внутренние `ui`, `model`, `api`, `lib`, `config`.

Для типов разрешён отдельный стабильный type-only public API по пути `<slice>/types`. Такой импорт должен использовать `import type`, например `import type { UserRole } from "@/entities/user/types"`. Путь `<slice>/types` является официальной вторичной точкой входа, а не разрешением на произвольный deep import.

Type-only public API может быть реализован файлом `types.ts` в корне slice или `types/index.ts`, который реэкспортирует публичные контракты из внутренних файлов. Внешние импорты вроде `<slice>/model/types`, `<slice>/api/types` и других внутренних путей запрещены. Внутри самого slice допустимы локальные относительные импорты типов.

Runtime public API должен экспортировать только контракт для внешних потребителей:

- компоненты, которые реально вставляются извне;
- runtime-функции или composables, являющиеся стабильным контрактом slice.

Type-only public API должен экспортировать только типы, необходимые внешним потребителям. Локальные типы реализации не публикуются.

Не экспортировать внутренние helpers, приватные mapper-функции, внутренние компоненты формы, DTO без внешней необходимости и технические детали реализации. Чем шире публичные API, тем сложнее безопасно менять slice.

## Размещение состояния, API и типов

Состояние размещается по владельцу ответственности:

- app-level состояние провайдеров и глобальной инициализации — в `app`;
- route/query/page-only состояние — в `pages`, если оно не стало самостоятельным блоком;
- состояние композиции блока — в `widgets`;
- состояние формы, pending/error/success и сценария действия — в `features`;
- состояние доменной сущности, cache, selected entity, нормализация данных — в `entities`;
- техническое состояние универсальных composables — в `shared`.

API размещается по смыслу запроса:

- базовый client и транспорт — `shared`;
- нейтральные запросы сущности — `entities`;
- команды конкретного действия — `features`;
- endpoint, существующий только для одного экрана или блока, можно временно оставить в `pages` или `widgets`, но если в нём появляется доменная модель или reuse, его нужно перенести ниже по ответственности.

Типы размещаются так же:

- доменные типы и DTO сущности — `entities`;
- типы формы или команды действия — `features`;
- типы композиции блока — `widgets`;
- route-level параметры — `pages`;
- generic contracts без домена — `shared`.

## Таблицы, списки и фильтры

Таблицы часто провоцируют ошибку “всё в widget”, поэтому размещать их нужно по уровням ответственности.

Базовая таблица находится в `shared`, если она не знает бизнес-сущностей, принимает данные и настройки как параметры, отвечает за механику отображения, slots, пагинацию, skeleton, mobile/desktop-поведение и generic controls.

Таблица сущности находится в `entities`, если она знает поля сущности, базовые колонки, status badge, форматирование полей и нейтральные фильтры сущности. Такая таблица не должна знать, что она находится в админке, реферальном разделе или конкретном сценарии.

Действия над таблицей находятся в `features`, если они создают, удаляют, экспортируют, блокируют, меняют статус, применяют bulk action или выполняют другой пользовательский сценарий.

Составной блок с таблицей находится в `widgets`, если он собирает entity table, toolbar, actions, фильтры, empty/loading/error states и контекст страницы. Если этот блок уникален для одной страницы и ещё не имеет самостоятельной ответственности, допустимо оставить композицию в `pages`.

Фильтры сущности размещаются в `entities`, если они описывают поля сущности и переиспользуются. Сценарные фильтры размещаются в `features`, если они являются частью действия или бизнес-процесса. Набор фильтров конкретного блока может собираться в `widgets`, но сами доменные определения не должны оставаться в widget.

## i18n и тексты

Переводы размещаются по тому же правилу ответственности:

- `shared` — инфраструктура i18n и универсальные фразы без домена;
- `entities` — поля, статусы, labels и базовые тексты сущности;
- `features` — тексты конкретного действия, формы, подтверждения, success/error сценария;
- `widgets` — заголовки и тексты составного блока;
- `pages` — заголовки, meta и тексты конкретного экрана;
- `app` — app-level shell, providers, глобальные сообщения запуска.

Не класть доменные термины в `shared` только потому, что они используются на нескольких страницах. Повторяемость доменного термина — признак `entities`, а не `shared`. Не дублировать один и тот же статус или label сущности в нескольких widgets.

## Частые нарушения

Толстый widget: внутри widget находятся типы сущности, API, таблица, formatter, actions, pagination и переводы. Исправление: entity-части перенести в `entities`, действия — в `features`, generic UI — в `shared`, а в widget оставить композицию.

Feature вместо widget: feature содержит заголовок секции, таблицу, несколько независимых actions и layout всего блока. Исправление: feature разбить на отдельные действия, а композицию перенести в `widgets` или `pages`.

Widget вместо feature: действие пользователя реализовано прямо в toolbar или строке widget. Исправление: вынести действие в `features`, а widget пусть только подключает его.

Entity знает сценарий: entity-компонент содержит admin-only кнопки, route navigation, permissions конкретного экрана или bulk actions. Исправление: оставить в entity нейтральное отображение, а сценарные части передавать сверху или подключать через features/widgets.

Shared знает домен: в `shared` появляются типы пользователя, статусы заказа, labels реферала или бизнес-условия. Исправление: перенести доменное в `entities` или `features`, оставить в `shared` только generic механизм.

Deep imports: внешний код импортирует внутренние файлы slice. Исправление: экспортировать нужный стабильный контракт через public API или не экспортировать, если это деталь реализации.

Дублирование таблиц: похожие таблицы одной сущности копируются в разные widgets/pages. Исправление: базовую механику держать в `shared`, доменное отображение в `entities`, контекстные actions и композицию — выше.

## Разбор жирного widget

Если widget стал слишком большим, разложить его по ответственности:

1. Найти доменные типы, DTO, мапперы, статусы, labels и форматтеры. Перенести в `entities`.
2. Найти нейтральные API-запросы сущности. Перенести в `entities/api`.
3. Найти API-команды действий. Перенести в соответствующие `features`.
4. Найти базовые UI-представления сущности. Перенести в `entities/ui`.
5. Найти универсальные UI-примитивы, таблицы, пагинацию, skeleton, generic filters layout. Перенести в `shared`.
6. Найти пользовательские действия. Выделить в `features`.
7. В widget оставить только сборку готовых частей, локальный wiring и layout блока.

Не выполнять большой глобальный рефакторинг без запроса. Разбирать нужно только затронутую область и только настолько, насколько требуется для текущей задачи.

## Когда не применять FSD механически

Не нужно создавать все layers заранее. Маленький frontend может начинаться с `app`, `pages`, `entities`, `shared`, а `features` и `widgets` добавляются при появлении реальных действий и самостоятельных блоков.

Не нужно создавать widget для каждого экрана. Если композиция уникальна, мала и не переиспользуется, она может остаться в page.

Не нужно создавать feature для каждой кнопки, если кнопка является чистым UI без сценарной логики. Но если у кнопки есть бизнес-действие, API-команда, permissions, validation, confirmation или сценарные тексты, это feature.

Не нужно переносить helper в `shared`, если он нужен одному slice. Локальная логика должна оставаться рядом с владельцем.

Не нужно дробить сущности искусственно. Entity должна соответствовать реальному понятию предметной области, а не каждому полю, вкладке или строке таблицы.

## Чеклист FSD-задачи

Перед завершением FSD-задачи проверить:

- слой выбран по причине изменения, а не по типу файла;
- page остаётся route-level экраном и не копит reusable бизнес-компоненты;
- widget содержит композицию, а не доменную модель, generic UI и действия с нуля;
- feature описывает действие пользователя или use case, а не целую страницу или большую секцию;
- entity содержит доменную модель и нейтральное отображение, но не сценарии верхних слоёв;
- shared не содержит доменных слов, статусов, ролей, бизнес-условий и entity-specific переводов;
- API, state, types, filters, tables и i18n размещены по владельцу ответственности;
- slices названы по бизнес- или продуктовому смыслу;
- используются только нужные segments;
- внешний импорт идёт через public API slice;
- нет deep imports во внутренние segments чужих slices;
- нет прямых cross-imports между slices одного layer;
- повторяющийся сценарий вынесен в feature, повторяющееся доменное отображение — в entity, повторяющийся generic UI — в shared;
- FSD внедряется в рамках запрошенной задачи без лишнего глобального рефакторинга.

## Уточнения после table refactor

- При финальном split широкого `widgets/*` slice нельзя оставлять compatibility slice со stores, helper-компонентами или page-facing re-export без явного deferred-решения в задаче. Если задача формулируется как завершение refactor, остаточные stores/helpers нужно перенести в конкретные widget slices до commit.
- После переноса helper-компонента между widget slices запрещено чинить сборку cross-import между widgets одного слоя. Нужно либо держать helper внутри конкретного slice, либо опустить общий контракт ниже по FSD, если он действительно переиспользуемый.
- При декомпозиции крупных Pinia stores после переноса domain state/actions нужно запускать lint до commit: длинные setup-функции разбивать на локальные helper factories с явными return types, не возвращая store обратно в широкий widget.
