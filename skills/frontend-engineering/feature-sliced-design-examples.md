
# FSD-примеры размещения по слоям

Эта заметка дополняет `feature-sliced-design.md` и нужна для разборов спорного размещения кода по слоям.

## Когда читать эту заметку

Читать после основной FSD-заметки, если:

- агент выбирает между `widgets`, `features`, `entities` и `shared`;
- в widget попали типы, API, таблицы, фильтры, колонки, действия или переводы;
- нужно разложить таблицу, список, toolbar, actions, bulk actions, фильтры или i18n;
- нужно исправить дублирование таблиц, entity UI или переводов между страницами;
- задача касается ревью FSD-структуры или переноса существующего frontend-кода.

Не читать для простых UI-правок без изменения архитектурных границ.

## Пример: админская таблица пользователей

Ситуация: нужен блок админки с таблицей пользователей, созданием пользователя, удалением, сменой роли, поиском и настройкой колонок.

Правильное распределение ответственности:

- базовая таблица, пагинация, skeleton, desktop/mobile-механика и column visibility без знания пользователя — `shared`;
- тип пользователя, DTO, статус, роль, форматирование имени, базовые колонки и нейтральная таблица пользователей — `entities/user`;
- создать пользователя, удалить пользователя, сменить роль, экспортировать пользователей — отдельные `features/user/*`;
- админский блок, который собирает таблицу, toolbar, actions, states и решает, какие действия доступны в этом контексте — `widgets/admin-users-table`;
- экран маршрута админки, который подключает блок и работает с route/query params — `pages/admin-users`.

Почему так: таблица как UI-механика не знает домен, пользователь как сущность не знает админский сценарий, действия имеют собственные состояния и API-команды, а widget только связывает готовые части в блок страницы.

Ошибка: положить тип пользователя, API получения, колонки, бейдж статуса, диалог создания, диалог удаления и пагинацию внутрь `widgets/admin-users-table`. Такой widget станет владельцем и домена, и действий, и generic UI, поэтому его нельзя переиспользовать и трудно менять.

## Пример: одна сущность в разных разделах

Ситуация: пользователи отображаются в админке, реферальном разделе и деталях проекта.

Размещение:

- общие поля пользователя, статус, avatar, display name и базовая строка/карточка — `entities/user`;
- реферальная привязка пользователя, если это отдельное доменное понятие, может принадлежать `entities/referral` или отдельной связанной сущности, а не виджету админки;
- действие “назначить пользователя рефералу” — `features/referral/assign-user`;
- админский список и реферальный список — разные widgets или page-level композиции, потому что их контекст, actions и toolbar отличаются.

Почему так: один и тот же пользователь не должен заново описываться в каждом разделе. Повторяемая доменная часть живёт в entity, контекстные действия — в features, а разные блоки страниц собирают их по-своему.

## Пример: фильтры

Фильтр по полю сущности принадлежит `entities`, если он описывает саму сущность и переиспользуется в разных сценариях. Например, фильтр по статусу пользователя или тарифу подписки — часть доменного представления сущности.

Фильтр принадлежит `features`, если он является самостоятельным пользовательским сценарием или несёт бизнес-логику действия. Например, “показать только пользователей для массового экспорта” или “подобрать кандидатов для назначения” может быть feature, если у сценария есть собственные правила, состояние и тексты.

Фильтр может собираться в `widgets`, если widget выбирает, какие entity-фильтры и feature-фильтры показать вместе. Но widget не должен становиться местом, где впервые описаны поля сущности и правила фильтрации.

## Пример: действия в строке таблицы

Ситуация: в строке пользователя есть кнопки “удалить”, “заблокировать”, “изменить роль”.

Размещение:

- строка пользователя, avatar, имя, статус и базовые поля — `entities/user`;
- каждое действие с confirmation, pending/error, API-командой и текстами — `features/user/delete`, `features/user/block`, `features/user/change-role`;
- widget решает, какие actions доступны в текущем блоке, и передаёт их в таблицу или row actions slot.

Почему так: строка таблицы не должна знать админские сценарии. Сущность отвечает за отображение пользователя, feature отвечает за действие, widget отвечает за контекстное подключение действия.

## Пример: таблица как feature
Таблица редко является feature сама по себе. Feature — это действие пользователя, а таблица чаще является либо standalone UI shell, либо отображением сущности, либо составным блоком.

Правильное правило:

- standalone table без домена — `shared/ui/standalone-table` или существующий эквивалент проекта;
- `UserTable` как отображение пользователей — `entities/user`;
- “экспортировать выбранных пользователей” — `features/user/export`;
- “таблица пользователей админки с toolbar и actions” — `widgets` или `pages`, если блок уникален и мал.

Исключение: таблица может быть частью feature, если сама таблица является интерфейсом конкретного действия. Например, выбор пользователей для одноразового назначения в сценарии может жить внутри feature, если таблица не является переиспользуемым отображением сущности и полностью подчинена этому действию.

Для проектирования reusable shell, slots и responsive table layout читать `standalone-table/README.md`.

## Пример: entity UI против feature UI

Entity UI показывает сущность без сценарного намерения: avatar пользователя, badge статуса, карточка заказа, строка подписки, форматированная сумма платежа.

Feature UI предлагает выполнить действие: создать пользователя, подтвердить платёж, отменить заказ, сменить тариф, отправить уведомление.

Если компонент отвечает на вопрос “что это за объект и как его показать?”, это `entities`. Если отвечает на вопрос “что пользователь сейчас делает с объектом?”, это `features`.

Пограничный случай: выпадающий список роли пользователя. Если это только отображение текущей роли, он принадлежит entity. Если через него пользователь меняет роль и запускает API-команду, это feature.

## Пример: i18n

Общие тексты вроде “сохранить”, “отмена”, “загрузка”, “ничего не найдено” относятся к `shared`, потому что они не знают домен.

Поля и статусы пользователя относятся к `entities/user`, потому что это язык сущности. Такие ключи нельзя копировать в админский widget или класть в `shared` только из-за reuse.

Тексты действия “создать пользователя”, “пользователь создан”, “не удалось удалить пользователя” относятся к соответствующей feature, потому что они меняются вместе со сценарием.

Заголовок блока “Пользователи админки” относится к widget, если это заголовок составного блока. Заголовок экрана относится к page, если он описывает route-level страницу.

## Пример: route navigation

Entity не должна знать, куда ведёт конкретная страница. Ссылка на профиль пользователя может быть нейтральным представлением только если маршрут является стабильной частью доменной навигации проекта. Если путь зависит от админки, реферального раздела, query params или контекста страницы, навигацию должен задавать widget или page.

Почему так: route context принадлежит верхним слоям. Если entity начнёт импортировать маршруты конкретных страниц, нижний слой станет зависимым от верхнего.

## Пример: layout, header и sidebar

Layout, header и sidebar отвечают за каркас интерфейса. Они могут размещать готовые feature-компоненты, но не должны реализовывать бизнес-действия напрямую.

Правильно по ответственности:

- переключение темы как универсальная app/user preference feature — `features/change-theme` или другой существующий slice по смыслу проекта;
- кнопка logout — feature авторизации;
- avatar текущего пользователя — `entities/user`;
- header/sidebar как композиция навигации и готовых действий — `widgets` или app shell, в зависимости от структуры проекта.

Ошибка: header напрямую знает store авторизации, API logout, настройки темы и доменные правила. В этом случае layout превратился в набор features и должен быть разложен.

## Пример: когда widget не нужен

Если страница содержит один небольшой уникальный блок, который не переиспользуется, не имеет собственного toolbar, сложных states и нескольких actions, можно оставить композицию в `pages`.

Widget нужен, когда блок можно назвать самостоятельной областью интерфейса, он имеет собственную структуру, собирает несколько нижних слоёв, повторяется или потенциально может быть перенесён на другую страницу.

Ошибка: создавать `widgets/*` автоматически для каждого экрана. Это даёт лишний слой без ответственности. Другая ошибка — держать в page большой повторяемый блок только потому, что он начался как маленькая разметка.

## Пример: разбиение entities

Не создавать entity для каждого поля, вкладки или части таблицы. Entity должна соответствовать устойчивому понятию предметной области.

Если “роль пользователя” является полем пользователя, она обычно остаётся внутри `entities/user`. Если роли имеют собственный lifecycle, отдельные API, права, списки и редактирование, тогда может появиться `entities/role`.

Если “реферальный пользователь” фактически тот же пользователь с дополнительным реферальным контекстом, не нужно дублировать `user`. Нужно отделить базового пользователя от реферальной связи или контекстного отображения.

Критерий: новая entity оправдана, когда у понятия есть самостоятельная модель, правила, API или reuse вне одного сценария.

## Пример: разбор жирного widget

Если в widget лежит всё сразу, разбирать его нужно не по папкам, а по смыслу:

- доменная модель, DTO, статусы и formatter — в entity;
- нейтральное отображение сущности — в entity;
- базовая таблица, pagination, generic controls — в shared;
- create/delete/change/export/confirm — в features;
- тексты действия — в features;
- тексты сущности — в entity;
- заголовок составного блока и wiring actions — в widget;
- route params, query sync и заголовок экрана — в page.

После разборки widget должен читаться как композиция: он берёт готовую сущность, готовые действия и generic UI, соединяет их в блок и задаёт контекст.
