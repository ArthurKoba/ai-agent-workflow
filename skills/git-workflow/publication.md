# Проверка и публикация

Перед первым коммитом в новом checkout и перед каждым push установи, какой
Git hook фактически активен (учитывая `core.hooksPath`), и проверь его
исполняемость и ожидаемую команду проекта. Установи отсутствующий hook
предписанным способом. Пройди необходимые локальные проверки. Не обходи
проваленный pre-push через `--no-verify` или подмену настроек.

На сервере настрой CI с запуском на push в основную ветку и на PR/MR,
когда такой процесс используется. Набор проверок (lint, формат, типы,
тесты, сборка) определяется действующим стеком и контрактом проекта;
bootstrap описан в [Project Bootstrap](../project-bootstrap.md).
CI при прямом push обнаруживает ошибку уже **после** обновления основной
ветки; локальные проверки и pre-push необходимы до публикации.
API-запись не запускает локальные hooks. Не объявляй проверки выполненными
без свидетельств и не обходи обязательные блокирующие проверки.

## Pull Request / Merge Request

Открывай PR/MR, если этого требуют правила защиты, ревью,
ограничения инструмента или явный запрос. Подготавливай связный diff. Черновой PR допустим до
завершения проверок, если его статус и непроверенные области явно обозначены.
Обновляй существующий PR того же объёма, а не создавай новый после каждой поправки.

Описание должно позволять ревью без восстановления всей переписки:
цель и связанный Issue, границы изменений, существенные решения или
совместимость, фактически проведённые проверки и результаты,
непроверенные места, риски и блокеры. Не выдавай сборку за runtime-проверку
или самостоятельный просмотр за независимое ревью. Обновляй описание при
существенном изменении объёма или результатов, избегая журнала микродействий.

При доступном разделении GitHub Apps используй `koba-ai-agent` для изменений
и `koba-ai-reviewer` для независимого ревью и разрешённого слияния.
Соблюдай установленное разделение полномочий: исполнитель публикует и
исправляет; независимый проверяющий оценивает и, где ему разрешено, сливает.
Автор не одобряет и не сливает собственный PR вопреки правилам проекта.
Перед слиянием проверяй актуальную головную ревизию и требуемые CI/review gates.

## Завершение и очистка

После включения изменений в целевую ветку обнови/закрой связанный Issue,
если его задачи действительно выполнены. Не удаляй Issues ради чистой
истории: ошибочно созданные записи допускается удалить только при наличии
полномочий и после проверки полезных связей и уникальных сведений.

Слитый PR/MR сохраняется как запись результата; ненужный неслитый —
закрывается, не удаляется вместо закрытия. Удаляй временную ветку и
локальные рабочие ресурсы только после проверки, что они не используются
и не хранят единственную копию незавершённой работы. Предлагай очистку
по окончании задачи, не выполняй рискованные удаления молча.
