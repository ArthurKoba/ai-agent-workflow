
# Python-стандарты

Эту заметку нужно читать при работе с Python-кодом, особенно перед изменением Python-файлов.

## Версия Python

- Использовать версию Python, объявленную репозиторием/toolchain.
- Предпочитать современный нативный синтаксис типизации, совместимый с минимальной поддерживаемой версией проекта.
- `from __future__ import annotations` добавлять только когда это требуется поддерживаемой версией, framework/runtime-поведением или существующей политикой проекта.

## Module Encapsulation

- Публичный API пакета должен экспортироваться через `__init__.py`.
- Implementation-модули должны быть приватными и иметь префикс `_`.
- Внешний код должен импортировать из пакета, а не из внутренних модулей.

Правильно:

```python
from db import DatabaseManager
from shared import BaseCliUtility
```

Нежелательно:

```python
from db._manager import DatabaseManager
from shared._cli import BaseCliUtility
```

## Типизация

- Типизировать публичные функции, методы, DTO/contracts и нетривиальные значения.
- Указывать типы параметров и возвращаемого значения там, где они являются частью поддерживаемого контракта или повышают проверяемость.
- Imports, используемые только для type annotations, держать под `TYPE_CHECKING`.
- Не переносить импорты под `TYPE_CHECKING` механически: некоторые фреймворки требуют annotations или referenced objects в runtime.
- Для структурированных данных не использовать `dict` и `tuple` в бизнес-логике.
- Для данных между слоями, сложных структур, API и JSON использовать Pydantic-модели или `dataclass`.
- Сырой JSON допустим только для полностью динамических данных без фиксированной структуры.
- Если структурированные данные проходят через `dict`/`tuple`/manual JSON, проверить, является ли это реальным contract smell. Рефакторить на typed model/dataclass только когда это улучшает поддерживаемую границу и входит в scope задачи.


- Для методов `Protocol` использовать `...`, а не `pass`.
- Для self-reference использовать синтаксис, поддерживаемый минимальной версией Python проекта; строковые forward references не добавлять без конкретной совместимости/runtime причины.

## Модели, типы и ошибки

- Хранить reusable DTO/dataclass/Pydantic contracts и ошибки в явно названных owner-модулях по структуре проекта, а не размазывать их по implementation-файлам.
- Иерархию ошибок строить от общей ошибки модуля/контекста к частным.
- Если репозиторий использует package public API, экспортировать только стабильные внешние contracts; детали реализации оставлять внутренними.
- Не проводить механический перенос существующих типов/ошибок только ради этого правила: сначала определить их фактического владельца и влияние на публичный API.


## Оформление ошибок и фабрики

- Ошибки должны быть информативными: сообщение должно объяснять конкретную ситуацию, а не только общий факт ошибки.
- В сообщении ошибки указывать ключевые аргументы сценария: `uuid`, `entity_uuid`, `status`, `operation`, `request_id` и другие поля, по которым можно понять, что именно не удалось обработать.
- Не передавать в ошибку полный пользовательский текст, секреты, токены, большие payload или персональные данные без необходимости. Для больших значений использовать длину или технический идентификатор.
- Для ожидаемых domain/service ошибок создавать отдельные классы ошибок, а не использовать `ValueError`, `RuntimeError` или общий Bare `Exception`.
- Если одна ошибка может возникать в разных сценариях, не собирать текст ошибки вручную в каждом месте вызова. Вместо этого добавлять на класс ошибки `@classmethod`-фабрики с именем `from_<scenario>`.
- Фабрика ошибки должна принимать предметные аргументы сценария, сама формировать сообщение и возвращать экземпляр `cls(...)`.
- Название фабрики должно отражать место или действие: `from_start`, `from_cancellation`, `from_status_update`, `from_count`, `from_external_response`.
- Не делать фабрики вида `from_message(message: str)`, если они просто прокидывают готовый текст. Такая фабрика не добавляет смысла и снова размазывает форматирование ошибки по коду.
- Если ошибка используется только в одном простом месте и сообщение не дублируется, фабрика не обязательна. Если сценариев несколько или сообщение содержит несколько аргументов, фабрика предпочтительна.
- Иерархия ошибок должна идти от общей ошибки модуля к частным ошибкам. Общая ошибка модуля должна наследоваться от `Exception`, частные ошибки — от общей ошибки модуля.

Пример:

```python
class JobServiceError(Exception):
    def __init__(self, message: str):
        super().__init__(message)


class JobNotFoundError(JobServiceError):
    @classmethod
    def from_start(cls, job_uuid: UUID) -> JobNotFoundError:
        return cls(f"Job not found for start: job_uuid={job_uuid}")

    @classmethod
    def from_count(cls, job_uuid: UUID) -> JobNotFoundError:
        return cls(f"Job not found while counting related records: job_uuid={job_uuid}")
```

Использование:

```python
if job is None:
    raise JobNotFoundError.from_start(job_uuid)
```

Нежелательно:

```python
if job is None:
    raise JobNotFoundError("Not found")

if job is None:
    raise JobNotFoundError(f"Error: {job_uuid}")
```

## Именование функций и docstring

- Использовать конкретные имена функций, которые ясно описывают назначение.
- Не использовать слишком общие названия; приоритет у длинных и чётких имён.
- Если имя функции полностью объясняет поведение, комментарий или docstring не нужен.
- Docstring нужен только для сложной логики, неочевидного поведения, ограничений или побочных эффектов.
- При рефакторинге убрать docstring, если он дублирует имя функции.
- Если комментарий объясняет действие лучше, чем имя функции, переименовать функцию и убрать комментарий, учитывая места использования.

## Импорты

- По умолчанию держать импорты в начале файла.
- Локальные импорты внутри функций использовать только при конкретной причине: optional dependency, runtime registration, дорогой import, platform branch или контролируемое разрешение цикла; причина должна быть понятна из контекста.
- Импорты сортируются группами: стандартная библиотека, сторонние пакеты, локальные модули.
- Многострочный формат также нужен, если строка импорта превышает 88 символов.

Пример правильного многострочного импорта:

```python
from integrations.provider import (
    ExternalUser,
    ExternalUserNotFoundError,
    ExternalUserStatus,
    ProviderSettings,
)
```

## Дублирование кода

- Избегать смыслового дублирования, которое создаёт несколько владельцев одного поведения.
- Не вводить абстракцию только по числу совпавших строк: выносить общий код, когда у повторов действительно один contract/причина изменения.
## Запуск команд и проверок

- Если репозиторий использует `uv`/lockfile-managed environment, запускать Python tooling через объявленный project runner (`uv run`, task runner или эквивалент), а не через случайное глобальное окружение.
- Не запускать широкие проверки после каждого микропатча. Выбирать проверки по риску изменения и repository acceptance policy.
- Перед commit/review/release выполнять требуемые проектом проверки и фиксировать, что именно они доказывают.
