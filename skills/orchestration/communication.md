# Прямая коммуникация и общее состояние

## Канал связи

Сначала используй доступные внутренние сообщения/сигналы между агентами и чатами. Для независимых сессий, браузера или отсутствующей прямой связи используй комментарии Issues. Проверь фактическую доставку, доступ участников и разрешение на сообщения; наличие инструмента само по себе не даёт полномочий. Дополнительный транспорт не требуется.

Участники задают вопросы, передают промежуточные контракты, находки и замечания друг другу напрямую. Не пересылай каждый обмен через координатора и не требуй его ACK для обычного уточнения. Координатор подключается при конфликте владения, зависимости, изменении общей цели или отсутствии прогресса.

## Один источник текущего состояния

При Git-координации обязательно используй [Git Workflow](../git-workflow.md). Назначенный Issue по умолчанию хранит восстанавливаемое состояние: цель, критерии, `work_id`, исполнителей, зависимости, решения, блокеры, принятые версии и следующий шаг. Проект может выбрать другой единственный источник. При внутренних сигналах существенные изменения тоже отражаются в нём; переписку целиком не копируй.

Описание Issue — короткий редактируемый индекс; комментарии — адресные обсуждения и существенные события. Код, CI, артефакты и runtime остаются владельцами своих доказательств. Не создавай параллельный Markdown-трекер и отдельный PDCA-статус-файл, дублирующий Issue. Без трекера выбери один доступный checkpoint, пригодный для восстановления.

Стабильный `work_id` обозначает функциональный результат и сохраняется при исправлениях, ревью и передаче. Для назначения нужны владелец и явная запись о принятии; повторное подтверждение на каждом возобновлении не нужно. Общий GitHub App-аккаунт не доказывает, что сообщения принадлежат одному агенту, и не даёт новых прав.

## События

Используй словарь проекта либо короткие метки:

| Метка | Назначение |
| --- | --- |
| ASSIGN / ACK | Назначение и принятие среза |
| WORKSPACE | Проверенные путь, ветка, HEAD, dirty state и доступные инструменты |
| UPDATE | Существенный промежуточный результат или новый контракт |
| REQUEST / ANSWER | Адресный вопрос и ответ с источником |
| BLOCKED | Причина, зависимость и что необходимо для продолжения |
| HANDOFF | Передача версии результата и свидетельств следующему участнику |
| ACCEPT / CHANGES_REQUESTED | Приёмка указанной версии либо конкретные замечания |
| CLOSE-WORK | Закрытие принятого функционального объёма |

В сообщении укажи `work_id`, автора/получателя, нужное действие или решение, версию и ссылки на источники/предыдущее сообщение, когда они существенны. Не создавай комментарий на каждую команду. Промежуточный результат помечай как неподтверждённый; он может помочь соседу начать работу, но не считается приёмкой.

## Возобновление и очистка

Прочитай индекс, существенные последние сообщения и относящиеся к срезу источники; специалисты сверяют свои refs/worktree. Восстанови владельцев, версии, незакрытые запросы и ближайший шаг. Оркестратор получает технические сведения от специалистов. Issue хранит состояние, но не запускает агентов: продолжение требует реального вызова. Не имитируй доставку или автоматическое пробуждение.

По завершении обсуждения обнови индекс и сохрани уникальные решения, свидетельства и незакрытые вопросы у их владельца. Отработанные комментарии редактируй/удаляй при доступной операции и полномочиях, предварительно сохранив значимые ссылки и происхождение выводов. Материальную ошибку исправь явно со ссылкой на прежнее утверждение. Если редактирование недоступно, добавь короткое уточнение и обнови индекс. Не уничтожай единственное доказательство ради чистоты переписки; закрытый Issue не требует удаления.
