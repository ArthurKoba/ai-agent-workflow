# Оркестрация агентов

Применяй при координации нескольких агентов, чатов, репозиториев или существенных срезов работы. Основа — адаптированный цикл Plan–Do–Check–Act (PDCA): планирование, реализация, проверка, закрепление результата. Число агентов и совмещение функций выбираются по задаче; шесть отдельных агентов не обязательны.

## Вход и обязательные правила

До запуска зафиксируй цель пользователя, границы текущего этапа, критерии приёмки, источники требований, доступные среды и ограничения. Уже согласованный с пользователем план можно использовать сразу. Не создавай повторное согласование обычных шагов внутри разрешённой задачи.

Оркестратор управляет процессом: назначает владельцев, следит за зависимостями, активностью агентов и выполнением плана. Сам код не исследует, не правит, не интегрирует и технически не перепроверяет. Решения о корректности получает от специалистов. Работа со статусом и обсуждение общей цели с пользователем допустимы.

Реализацию и анализ/приёмку одного среза разделяй. Исполнитель проверяет свою работу, но это не независимая приёмка. Исключения с совмещением исполнителя и аналитика допускаются только по явному разрешению пользователя; смена функции сама по себе не создаёт независимость.

## Что читать

- Всем участникам → [функции и совмещение](participants.md), [цикл и приёмка](cycle.md).
- Для обмена заданиями, вопросами и результатами → [прямая коммуникация](communication.md).
- При параллельной работе, исследовании и интеграции → [поток задач](pipeline.md).
- Для длительного общего Issue и сохранения уроков → [завершение рабочего пространства](workspace.md).
- При любой Git/Issue-оркестрации обязательно прочитай [Git Workflow](../git-workflow.md); участники операций тоже читают его. Он владеет ветками, коммитами, публикацией и жизненным циклом Issues.
- Для технической приёмки обязателен [скилл ревью](../code-review.md); каждый специалист дополнительно загружает предметные скиллы своего среза.
- При проектировании документации и наборов контекста → [Context Engineering](../context-engineering.md).

Описанные здесь роли — функции внутри скилла. Отдельного слоя файлов ролей нет. Полномочия Git-аккаунтов задаются проектом и инструментами, а не выбранной функцией.

## Основание подхода

Адаптация идеи [PDCA Алексея Ширшова](https://github.com/AlexeyShirshov/skills/tree/main/skills/pdca), изложенной в статье [«Вайбкодинг: что дальше?»](https://habr.com/ru/articles/1098676/). Это самостоятельные правила: гибкое совмещение аналитических функций, отдельный исполнитель, прямая связь участников и состояние в выбранном проектом источнике. Внешний PDCA служит ссылкой на происхождение идеи, не дополнительным обязательным слоем инструкций.
