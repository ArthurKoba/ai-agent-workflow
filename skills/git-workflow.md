# Git Workflow

Универсальные правила работы с Git, Issues, ветками, коммитами и PR/MR.
Загружай этот навык при Git-операциях, работе с Issues и Git-оркестрации.
Проектные правила, разрешения и возможности инструмента имеют приоритет
над настройками по умолчанию.

## Задачи и состояние

Если Git-платформа предоставляет Issues (или штатный трекер) и доступ к ним
разрешён, используй его по умолчанию для значимых задач, улучшений, backlog
и roadmap, если проект не предписывает другой источник состояния. Issue хранит
актуальные цели, границы, решения, владельцев, зависимости, блокеры и
следующий шаг. Группируй связанные мелкие исправления; не создавай Issue
на каждую попытку и не копируй в него историю вызовов инструментов.

Обновляй прежде всего редактируемое описание Issue; комментарии используй
для существенных решений, обсуждения агентов и handoff. Не добавляй микрологи.
Редактировать/удалять неактуальные комментарии можно, только когда платформа
это позволяет и уникальные сведения или связи не теряются.

Артефакты и доказательства хранятся у своего владельца, Issue ссылается на них.
Формат отчётности определяет [Reporting Protocol](../docs/REPORTING_PROTOCOL.md),
управление контекстом — [Context Engineering](context-engineering.md).
Для координации агентов обязательно прочитай [Оркестрацию](orchestration/README.md):
она владеет назначениями, прямым общением, протоколом событий и handoff.
Не дублируй эти правила здесь.

## Ветка и рабочее окружение

1. Проверь репозиторий, основную ветку, актуальную базу, ограничения,
   состояние checkout и существующие изменения. Не теряй начатую работу.
2. Для незащищённой основной ветки предпочитай прямой push, **только если**
   проектные правила и выбранный инструмент это разрешают. При защите,
   обязательном ревью или запрете инструмента используй рабочую ветку и PR/MR.
   Не обходи запреты через другой способ публикации.
3. Группируй связанные изменения одним логическим объёмом/PR, когда он нужен;
   разделяй действительно независимые задачи и пересекающееся владение.
4. Предпочитай локальный цикл «изменение → проверка → исправление» и
   одну пакетную публикацию, а не CI/PR после каждой мелкой правки.

При параллельной работе используй независимые worktree/workspace и
согласованные владельцы пересекающихся участков. Для handoff сохраняй
точную идентичность незавершённого diff/коммита.

## Модули операций

- Перед созданием коммита обязательно прочитай [Коммиты](git-workflow/commits.md).
- Перед проверкой к публикации, PR/MR, push, слиянием и итоговой очисткой обязательно прочитай [Публикацию и завершение](git-workflow/publication.md).

Загружай модуль целиком для соответствующей операции, не все модули заранее.
