# Git Workflow

Универсальные правила работы с Git, Issues, ветками, коммитами и PR/MR.
Загружай этот навык при Git-операциях, работе с Issues и Git-оркестрации.
Проектные правила, разрешения и возможности инструмента имеют приоритет
над настройками по умолчанию.

## Задачи и состояние

Если Git-платформа предоставляет Issues (или штатный трекер) и доступ к ним
разрешён, используй его по умолчанию для значимых задач, улучшений, backlog
и roadmap, если проект не предписывает другой источник состояния. Issue хранит
актуальные цели, границы, решения, владельцев, зависимости, блокеры и
следующий шаг. Группируй связанные мелкие исправления; не создавай Issue
на каждую попытку и не копируй в него историю вызовов инструментов.

Обновляй прежде всего редактируемое описание Issue; комментарии используй
для существенных решений, обсуждения агентов и handoff. Не добавляй микрологи.
Редактировать/удалять неактуальные комментарии можно, только когда платформа
это позволяет и уникальные сведения или связи не теряются.

Артефакты и доказательства хранятся у своего владельца, Issue ссылается на них.
Формат отчётности определяет `docs/REPORTING_PROTOCOL.md`,
управление контекстом — `skills/context-engineering.md`.
Назначения агентов, протокол событий и handoff принадлежат
`roles/ORCHESTRATOR.md` — не дублируй их здесь.

## Ветка и рабочее окружение

1. Проверь репозиторий, основную ветку, актуальную базу, ограничения,
   состояние checkout и существующие изменения. Не теряй начатую работу.
2. Для незащищённой основной ветки предпочитай прямой push, **только если**
   проектные правила и выбранный инструмент это разрешают. При защите,
   обязательном ревью или запрете инструмента используй рабочую ветку и PR/MR.
   Не обходи запреты через другой способ публикации.
3. Группируй связанные изменения одним логическим объёмом/PR, когда он нужен;
   разделяй действительно независимые задачи и пересекающееся владение.
4. Предпочитай локальный цикл «изменение → проверка → исправление» и
   одну пакетную публикацию, а не CI/PR после каждой мелкой правки.

При параллельной работе используй независимые worktree/workspace и
согласованные владельцы пересекающихся участков. Для handoff сохраняй
точную идентичность незавершённого diff/коммита.

## Коммиты

Формируй логические коммиты по завершённым изменениям, а не по каждой попытке.
Просмотри фактический staged diff; убедись, что в нём нет чужих, случайных
или несвязанных файлов. Сообщение описывает полезный смысл изменения,
а не служит отчётом о процессе.

Если проект не установил иной формат, используй Conventional Commits:

```text
<type>[optional scope]: <short imperative summary>

<body explaining meaningful changes and why, when needed>

[optional footer]
```

- Заголовок — конкретный, на английском, в повелительном наклонении,
  обычно до 50–72 символов; без точки, заглушек `update`, `fix` или `wip`.
- Тип выбирай по главному эффекту: `feat`, `fix`, `refactor`, `perf`,
  `test`, `docs`, `style`, `build`, `ci`, `chore`, `revert`.
  В монорепозитории `scope` обязателен и указывает сервис или компонент;
  в обычном репозитории он необязателен, если местные правила не строже.
- Тело нужно, когда заголовка недостаточно для понимания значимых
  изменений, причин, контрактов или ограничений. Для тривиального diff
  достаточно заголовка. Не перечисляй построчно файлы и операции.
- При наличии тела отделяй его пустой строкой; footer используй для
  ссылок на Issue, breaking changes и других необходимых метаданных.
- Несовместимость отмечай `!` и `BREAKING CHANGE:` с объяснением
  последствия и требуемой миграции.

Примеры:

```text
docs(git): define issue and pull request lifecycle

Keep task state in Issues and prefer local validation before publication.
Clarify branch cleanup and separate reviewer ownership.
```

```text
docs: fix broken skill link
```

## Проверка и публикация

Перед первым коммитом в новом checkout и перед каждым push установи, какой
Git hook фактически активен (учитывая `core.hooksPath`), и проверь его
исполняемость и ожидаемую команду проекта. Установи отсутствующий hook
предписанным способом. Пройди необходимые локальные проверки. Не обходи
проваленный pre-push через `--no-verify` или подмену настроек.

На сервере настрой CI с запуском на push в основную ветку и на PR/MR,
когда такой процесс используется. Набор проверок (lint, формат, типы,
тесты, сборка) определяется действующим стеком и контрактом проекта;
bootstrap описан в `skills/project-bootstrap.md`.
CI при прямом push обнаруживает ошибку уже **после** обновления основной
ветки; локальные проверки и pre-push необходимы до публикации.
API-запись не запускает локальные hooks. Не объявляй проверки выполненными
без свидетельств и не обходи обязательные блокирующие проверки.

## Pull Request / Merge Request

Открывай PR/MR, если этого требуют правила защиты, ревью,
ограничения инструмента или явный запрос. Подготавливай связный diff. Черновой PR допустим до
завершения проверок, если его статус и непроверенные области явно обозначены.
Обновляй существующий PR того же объёма, а не создавай новый после каждой поправки.

Описание должно позволять ревью без восстановления всей переписки:
цель и связанный Issue, границы изменений, существенные решения или
совместимость, фактически проведённые проверки и результаты,
непроверенные места, риски и блокеры. Не выдавай сборку за runtime-проверку
или самостоятельный просмотр за независимое ревью. Обновляй описание при
существенном изменении объёма или результатов, избегая журнала микродействий.

Соблюдай установленное разделение полномочий: Implementer публикует и
исправляет; независимый Reviewer оценивает и, где ему разрешено, сливает.
Автор не одобряет и не сливает собственный PR вопреки правилам проекта.
Перед слиянием проверяй актуальную головную ревизию и требуемые CI/review gates.

## Завершение и очистка

После включения изменений в целевую ветку обнови/закрой связанный Issue,
если его задачи действительно выполнены. Не удаляй Issues ради чистой
истории: ошибочно созданные записи допускается удалить только при наличии
полномочий и после проверки полезных связей и уникальных сведений.

Слитый PR/MR сохраняется как запись результата; ненужный неслитый —
закрывается, не удаляется вместо закрытия. Удаляй временную ветку и
локальные рабочие ресурсы только после проверки, что они не используются
и не хранят единственную копию незавершённой работы. Предлагай очистку
по окончании задачи, не выполняй рискованные удаления молча.
