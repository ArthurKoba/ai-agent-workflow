# ZITADEL direct Coolify Traefik acceptance

**Historical evidence:** the standalone Koba topology, direct Traefik routes, Login V2 and issuer/JWKS were checked on Coolify v4.5.3 on 2026-11-02 with an explicit fixed hostname. The **updated portless-FQDN example** is source-only until verified in the intended Coolify parser/runtime; the shared-dependency variant has not been deployed. Neither variant has completed live user login/logout, authenticated gRPC API, backup-restore or failure recovery acceptance.

1. **Services:** standalone resolves `postgres`, `valkey`, `zitadel-api`, `zitadel-login` plus three named volumes (explicit `driver: local` in Coolify); shared resolves only `zitadel-api`, `zitadel-login` and `zitadel-bootstrap` (explicit `driver: local` in Coolify). Neither includes `gateway`, `zitadel-gateway` or `Caddyfile`; no private host-published ports.
2. **Actual Coolify parser:** `extends` retains healthchecks, dependencies and volumes. The API declares exactly one route via `SERVICE_FQDN_ZITADEL_API_8080: /` to port 8080. The **unsuffixed** `${SERVICE_FQDN_ZITADEL_API:?}` must resolve to the current hostname from the API service's HTTPS Domains, with **no scheme or port**; inspect Deployable Compose, issuer, Login Host and both Traefik router rules. Never use the port-suffixed value as an identity hostname, even if it resolves to `host:8080`. Coolify 4.5.3 previously required an explicit hostname in the live Koba deployment; if this parser lacks a correct portless variable, stop and use a version-proven configuration instead of assuming auto-resolution. No duplicate public domain input or hardcoded generic hostname.

3. **Traefik route table:** Inspect generated and custom HTTPS routers, HTTPS entrypoint and certresolver, priority 200 Login route, priority 100 API route, API loadbalancer `h2c:8080`, Login `http:3000`. Prove both services are on a proxy-reachable Docker network and normal generated routers cannot intercept requests unexpectedly. If there is another ZITADEL instance on the same proxy, use unique names for its custom routers/services. Fail if a router overwrites another instance.
4. **Security:** Verify requested HTTP redirects/TLS, single issuer hostname, no direct host-port exposure, no unintended public `/debug` or equivalent diagnostic endpoint. This version does not implement Caddy's old `/api` prefix stripping or `/` redirect; verify application paths and add reviewed routing only if required.
5. **Dependencies:** Confirm the Login PAT is written and readable across API/Login through the shared named volume. UID `0` is currently used because live Coolify local named volume's root ownership caused PAT write `permission denied` and partial instance migrations with unprivileged API. A non-root replacement must be specifically tested; verify in both standalone and shared variants. On partial first-init failures, preserve master key, back up the dedicated database, and recover carefully; never delete unique constraints speculatively. Standalone API DSN resolves `postgres` through the common resource network; avoid aliases on a separate per-service Compose network. Check actual Docker network membership/DNS from a peer container, not only the source Compose.  For standalone Valkey, its ACL-protected healthcheck **must** set `REDISCLI_AUTH="$VALKEY_PASSWORD"`, not `VALKEYCLI_AUTH`, before running `valkey-cli ping | grep -qx PONG`. This was verified against the real Valkey 8.1.10 container on 2026-11-02 (`VALKEYCLI_AUTH` returned `NOAUTH`, `REDISCLI_AUTH` returned `PONG`). Standalone PostgreSQL and Valkey healthchecks pass before API. Shared Postgres role/database, network DNS and Valkey ACL/cache index ownership must be proven before deployment; don't assume they are provisioned automatically.
6. **Identity:** API and Login V2 healthy; issuer discovery and JWKS have the correct HTTPS origin; exercise real OIDC login/logout, Login PAT access and API calls needing h2c/gRPC forwarding, not only console HTML.
7. **Cache / persistence:** `Instance`, `Milestones`, `Organization` caches use Redis; verify `DBOffset` index selection and temporary cache failure. Test first start, repeat deploy, host restart, volume persistence, backups/restore and migration rollback limitations.
8. **Observability (if enabled by deployment owner):** prove fresh ZITADEL traces/logs/metrics in the approved receiving backend. The receiving collector and credentials are not automatically supplied by these public presets.

Do not expose plaintext secrets, PAT or private keys in logs, tests or Git. Runtime results belong in the owning private infrastructure repository.
