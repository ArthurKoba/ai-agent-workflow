# ZITADEL single-domain Caddy acceptance

**Evidence boundary:** Koba's 2026-11-02 deployment used direct Traefik routes, not these Caddy presets. A source-valid Compose or a healthy container is not proof of working login or native gRPC. The shared-dependency Caddy variant has not been runtime-deployed.

1. **Topology:** standalone has five Compose services: PostgreSQL, Valkey, `zitadel-core`, `zitadel-login`, `zitadel-api` (Caddy), with three named volumes. Shared-dependency has the three identity services and `zitadel-bootstrap`. Neither exposes internal service ports on the Docker host.
2. **Coolify parser:** only `zitadel-api:8080` owns a public HTTPS domain with path `/`; its only magic route is `SERVICE_URL_ZITADEL_API_8080: /`. There are no manually assigned Login domains or custom Traefik labels. Verify `extends` resolves services, healthchecks and volumes, and the portless `SERVICE_FQDN_ZITADEL_API` matches the real external issuer hostname.
3. **Caddy routes:** inline Caddyfile listens on port 8080. `/ui/v2/login` and descendants retain the original prefix when proxying to `zitadel-login:3000`; other requests are forwarded via `h2c://zitadel-core:8080`. Both internal upstreams must resolve by service DNS. No separate Caddyfile mount or Coolify Files entry is needed.
4. **HTTPS consumers:** `/.well-known/openid-configuration` and `/oauth/v2/keys` return the intended HTTPS issuer/JWKS; `/ui/v2/login/healthy` comes from Login V2 rather than the API 404; `/ui/console/` reaches ZITADEL Core. Verify real login/logout, sessions, cookies and tokens, not just HTTP status codes. Audit exposed diagnostic paths.
5. **Native gRPC:** even with Caddy-to-Core h2c, verify the Coolify/Traefik-to-Caddy hop preserves HTTP/2 for real authenticated gRPC traffic. Mark gRPC unaccepted until tested end to end.
6. **Bootstrap and durable state:** Core creates the Login PAT in the named bootstrap volume and Login reads it. UID 0 remains in these examples because Coolify local named volume ownership previously blocked an unprivileged Core. Do not reset partially initialized databases, delete PAT volumes, or rotate the master key merely to retry bootstrap.
7. **Dependencies:** standalone uses PostgreSQL `postgres:5432` and protected Valkey ACL; the Valkey healthcheck must set `REDISCLI_AUTH` rather than `VALKEYCLI_AUTH`. Shared-dependency requires provisioned restricted PostgreSQL identity/database, Valkey ACL and reserved DBOffset cache indexes, plus actual private-network connectivity. The URL `/0` does not select all cache-purpose DB indexes.
8. **Recovery:** confirm cold restart, repeat deploy, host restart, Redis/cache failure, backups and restore of PostgreSQL, PAT volume and protected master key. If enabled, verify actual OTLP telemetry separately. Never disclose protected credentials in logs or Git.
